A forensic CI audit does not measure your code: it measures the instrument you use to decide whether your code is fine. It does not trust GitHub's rollup; it re-audits it with anchors pinned to head.sha, a declared limit and a negative control.

Declared delta. An earlier published run gave 236 / 115 / 33 and kept no raw file. The frozen census gives 240 / 121 / 34 (+4 / +6 / +1). The difference is not reconciled by hand, and the universe does not explain it: the census lists fewer PRs (1,598) than the snapshot (1,602) and still counts more reds.

The mechanism that gives the method its value: in 34 PRs the rollup read green while the red shard sat beyond the API window. A sweep that reads only the first window reports a false zero. That false zero was caught in-house first.

What this case does not claim

  • It does not claim the red is «infrastructure blocking code». Kernel-vs-test attribution of the signed-zero cluster is unresolved: the inspector returns INDECIDIBLE.
  • It does not claim 115 distinct bugs. Three mechanisms hold 86% of the 114 classified; the «systemic» criterion is declared, not decorated.
  • The TT_FATAL cluster was fixed upstream on 2026-10-20 (#61470): those branches are 13–65 commits behind, stale base, not an unfixed defect.
  • The «143 false greens» figure from the previous run does not reproduce. 34 is published because it is what can be re-audited today, from a carrier.
